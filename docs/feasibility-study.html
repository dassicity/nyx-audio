The Lossless Pi

A private, lossless music library on a Raspberry Pi 5 — served over the home network, played on the machine in your hands.

V1 · Straightforward V2 · Sourcing is the risk V3 · iOS is the gate
Pi 5 · 4GB · headless Audio decodes client-side FLAC · 16/44 → 24/192
01 — Verdict

The idea works. The hard parts are not where you think.

A Pi 5 serving FLAC over a LAN is not a demanding job. One FLAC stream is roughly 1 Mbps — about 0.1% of your gigabit Ethernet, and well inside what Wi-Fi handles. Compute is not your constraint. Storage, sourcing, and browser playback are.

Version 1 is a weekend, not a project

Copy files to the Pi, run a library server, point a browser at it. This part is genuinely solved. Your entire effort should go into the interface and the playback engine, because that is the only part that doesn't already exist in a form you'd be happy with.

Version 2's difficulty is legal and logistical, not technical

The code that searches, downloads, tags and imports music is a few hundred lines glued to existing tools. What you cannot engineer around is that lossless files are not freely and instantly available on demand. Soulseek transfers are queue-dependent and slow; purchased downloads have no API; free legal catalogues are deep but narrow. The fantasy of "type a name, hear it in lossless three seconds later" does not exist at any price. What you can build is better than nothing and, designed right, better than waiting.

Version 3 hinges on one platform limitation

An installed web app on Android or desktop is a real music player. On iOS, background audio from a browser-based app is unreliable — playback stops when the screen locks or you switch apps. If you listen on an iPhone, that single fact is what forces a native shell (Flutter, React Native) rather than a progressive web app. Decide which phone matters before you write the client, because it changes the answer completely.

02 — Consequences

What "the Pi never touches audio" already settled for you

Choosing to decode on your laptop and phone — the Pi purely as a file and metadata server — removes a large amount of complexity, and adds one honest limitation. Worth being explicit about both.

What you gained

No DAC decision. The Pi 5 has no analog audio output at all — the 3.5mm jack was dropped from the board. Had the Pi been the player, you'd be choosing between a USB DAC and an I2S HAT before writing a line of code. You skip that entirely.

The GPIO header stays free, so an NVMe HAT can have it without fighting a sound card for space.

The Pi runs headless — no ALSA configuration, no exclusive-mode device locking, no audio group permissions, no clicks and pops to debug at midnight.

What you gave up

Bit-perfect playback. A browser hands audio to the operating system's mixer, which resamples everything to one rate — usually 48kHz. Your 44.1kHz FLAC gets converted on the way out. This is audibly fine and it is what every streaming service already does to you.

But say so in the interface. Showing FLAC 16/44.1 → output 48kHz instead of a vague "HD" badge is the cheapest way to make software feel like it was built by someone who cares. If you ever want true bit-perfect, that is a native desktop client, not a web page — a later chapter, not a v1 compromise.

03 — Hardware

Three things the hardware will do to you

Storage

A 64GB microSD is roughly 150 albums, and that is before the operating system takes its ten. A CD-quality FLAC album runs 250–400MB; a 24/96 release runs 1–2GB. You will hit the ceiling faster than you expect, and you will hit it in the middle of a transfer.

Worse, SD cards wear out under a server's write pattern — database updates, logs, library rescans. This is the single most common way a Pi server dies. Move the library, and ideally the whole system, to an SSD: either the official M.2 HAT+ (note it only fits short 2230/2242 drives) or a USB 3.0 SSD. With no sound card competing for the header, the NVMe route is now clean.

Wiring & power

Put the Pi on Ethernet. Bandwidth was never the issue; reliability is. A server that drops off Wi-Fi mid-album while you are on the sofa is the fastest way to abandon a project.

Use the 27W (5V/5A) USB-C supply if you hang an SSD off the USB ports, and give the Pi 5 active cooling — it throttles without it, and a throttled server during a library scan is a slow, confusing kind of broken.

The spare Pi

Don't leave it in a drawer. In order of usefulness to this project: a staging box, so you never deploy an untested build to the machine you actually listen on; a backup target, running a nightly snapshot of the library; and in v2, the ingest worker — downloading, fingerprinting, tagging and transcoding, kept off the machine that serves you music so a heavy import never stutters playback.

A fourth option, if you ever put speakers in another room: a synchronised playback endpoint. Set that aside for now — it contradicts the client-side model you just chose, and it is a project of its own.

04 — Architecture

Do not write the backend

The strongest thing you can do for this project is refuse to build the boring 80%. A library server — scanning folders, parsing tags, extracting cover art, handling users, transcoding, serving range requests — is thoroughly solved and profoundly unrewarding to rewrite.

Run Navidrome: a single Go binary, small enough that a Pi 5 with 4GB is comically overqualified, speaking the Subsonic / OpenSubsonic REST API. Then build only the client, which is the part you actually care about and the part worth designing.

The underrated benefit While you are building your own interface, every existing Subsonic client works against your server for free — on your phone, in the car, on a desktop. You are never blocked on your own unfinished UI to listen to your own music. That alone will decide whether this project survives month two.

What you're giving up by not rolling your own

The Subsonic API is old and its data model is opinionated — it thinks in artists, albums and tracks, and it will resist anything genuinely novel you want to model, like moods, listening contexts, or your own embeddings. The right answer is a thin service of your own alongside Navidrome that owns the interesting data and defers to Navidrome for the boring parts. Not a fork. A sidecar.

The state model that decides how far this can go

Make the queue live on the server, not in the browser tab. Clients render server state and send intents; they don't own playback. This costs almost nothing in v1 and it is what makes "pick up on my phone where the laptop left off" a small feature later instead of a rewrite. Audio still decodes locally — only the queue and position are shared.

Roadmap

Three stages

V1
It plays
Local library, browsed and played in a browser on your own machine.

The engineering that will actually cost you time

Gapless playback. This is the real technical challenge of v1, and it is easy to underestimate. An HTML <audio> element will not do it — swapping sources leaves an audible seam, which ruins live albums, DJ mixes, and most classical and progressive music. The workable approach is the Web Audio API: decode the next track into an audio buffer ahead of time and schedule it on the audio clock at an exact offset from the current one. A five-minute 16/44 track is about 50MB decoded, which is fine to hold in memory. Media Source Extensions with FLAC is the alternative, and it is well-supported in Chrome and shaky everywhere else.

Loudness normalisation. Scan the library for ReplayGain / EBU R128 values and apply them, with a track-versus-album toggle. Without it, a 1970s pressing and a modern remaster differ by ten decibels and every shuffle is a jump scare. With it, the whole thing feels professionally made. This is a background job, not UI work, and it is the highest ratio of perceived quality to effort in the entire project.

Media Session API. Two hours of work to make your laptop's media keys, lock screen, and Bluetooth headphone buttons control your player. It is the difference between "a web page that plays music" and "an app".

The design decisions that matter more than the code

  • Make the album the primary object. Nearly every self-hosted player defaults to an infinite track list, because tracks are what the database has. Someone who collects FLAC listens to albums. Build the album view first and treat the track list as secondary.
  • Show the signal path. Source format, bit depth, sample rate, whether it is being transcoded, what the output is actually running at. Nobody does this well and it costs almost nothing.
  • Keyboard first. Space, arrows, / to search. You are the only user; optimise for you.
  • Resume everything. Reload the tab, come back tomorrow, and the queue and position are exactly where you left them.

Do the ingest work before you copy a single file

Run your collection through beets first: it matches releases against MusicBrainz, fixes tags, fetches cover art, and enforces one folder convention. Garbage metadata produces a garbage interface, and no amount of design rescues an album view where the same artist appears four times under four spellings. Scan ReplayGain values in the same pass. Decide your layout once — Artist/Album (Year)/NN - Title.flac — and never think about it again.

Reach it at http://music.local via mDNS. Back it up from night one — the library is the irreplaceable asset here, not the code.

V2
It finds things
Search reaches past your shelves and brings music back.

Where lossless music actually comes from

Four tiers, and they behave completely differently:

  • Purchased downloads. Bandcamp is the best of these — FLAC up to 24/192, re-downloadable forever, and the largest share to the artist. Qobuz's download store covers mainstream and hi-res catalogue; Presto for classical, Beatport and Bleep for electronic. None of them offer a purchase API, so automation stops at a watched folder: you buy, the folder ingests.
  • Free and legal. The Internet Archive's Live Music Archive holds an enormous quantity of lossless, legitimately traded concert recordings, and it has a real API. This is the one source you can automate end to end with no asterisk. Free Music Archive, Jamendo and MusOpen cover the rest.
  • Your own discs. A USB optical drive on the spare Pi plus secure ripping with AccurateRip verification gives you the highest-quality, lowest-risk files in existence. Unglamorous, which is exactly why a genuinely good "CD ingest station" would be a distinctive feature.
  • Soulseek. You already use it via Nicotine+. The piece you want is slskd — a headless Soulseek daemon with a REST API, which is the integration point that makes automation possible at all. The common pipeline is a wanted-list manager feeding slskd through a bridge, then importing into the library. Be clear-eyed: this is unlicensed distribution, availability is inconsistent, and transfers depend on a stranger's upload queue.
The design problem underneath None of these sources are instant. So stop designing for instant. The interesting product question is not "how do I make downloads fast" — it is "what should the interface do during the twenty minutes a download takes?"

Three features that answer that question

  • One search bar, tiered results. Type once and see In your library / Free and legal / Available to buy / Findable elsewhere as visibly distinct tiers. One tap means "I want this." A background worker fulfils it and tells you when it lands. The wishlist is the product, not a consolation prize.
  • Lossy now, lossless later. The genuinely novel one. When you want something you don't have, start playing an immediately-available lossy source while the FLAC is acquired in the background, then silently upgrade the library entry when it arrives. The queue never blocks on a download. This is what makes it feel like a streaming service without lying about how fast downloads are.
  • A transcode detector. A large share of "FLAC" in the wild is an MP3 in a costume. Run a spectral check on every incoming file — a lowpass energy heuristic catches a hard cutoff at 16kHz instantly — and flag or reject it before it pollutes your library. This is a real problem that real collectors deal with manually, and automating it is a clear differentiator.

Everything arriving should pass through beets automatically: MusicBrainz match, acoustic fingerprint fallback, cover art, ReplayGain, then a library rescan. Import quality is what separates a collection from a folder.

V3
It's in my pocket
A real client on the phone, on and off the home network.

Two gates to clear first

HTTPS. Installable apps and offline caching require a secure context, and you cannot get a public certificate for a private IP address. Two clean paths: a mesh VPN that issues real certificates and also solves remote access outside the house, or your own domain with a DNS-based certificate challenge pointing at the private address. Solve this before you write the client; it is not an afterthought.

Background audio. Covered above, and it is the fork in the road. Android and desktop are fine as an installed web app. iPhone is not — background playback needs a native shell with a proper audio-service integration. If iOS matters, budget for Flutter or React Native and treat the web app as the desktop client rather than trying to make one codebase do both badly.

What the phone unlocks

  • Offline albums. Store FLAC where space allows, else transcode to Opus server-side. The Pi 5 does that far faster than real time.
  • Network-aware quality. Lossless on the home network, Opus on cellular, switching automatically — and visibly, so you always know which one you're hearing.
  • Handoff. Because the queue lives on the server, moving from laptop to phone mid-album is one tap. This is the feature that makes the whole system feel like one thing rather than three clients.
05 — The shelf

Where this stops being a Navidrome skin

You asked what would make it innovative. These are ordered roughly by payoff per hour. Pick two or three — a system that does a few unusual things exceptionally is far better than one that does everything adequately.

Time-synced lyrics

High payoffLow effort

LRCLIB offers around three million synced lyrics through a free API with no key and no account. A full-screen, well-typeset lyrics view is the single highest-delight feature available to you, and it is an afternoon's work.

Natural-language library search

High payoffMedium effort

"Something quiet for the evening." "Like Talk Talk, but earlier." Precompute embeddings of metadata and reviews on your laptop, store the vectors in SQLite next to the library, query them on the Pi. No GPU, no cloud, no subscription. This is the feature nothing else has.

Cover-art-driven interface

High payoffLow effort

Extract a dominant colour from the current album's artwork and let the accent, the now-playing surface and the progress bar take it. The interface becomes the record you're playing. Constrain saturation so it never fights legibility.

Crate-digging mode

DistinctiveLow effort

An explicit anti-algorithm: one album at a time from what you haven't played in a year, no infinite scroll, no recommendations. You bought this music deliberately. The most valuable thing a private library can do is remind you what's in it.

Tap-to-play NFC cards

DelightfulMedium effort

Print album art onto NFC cards for about thirty cents each. Tap one with your phone and the album starts. Phones read NFC natively, so this needs no extra hardware at all — and it restores the physical, deliberate act of choosing a record.

Party queue by QR code

SocialLow effort

Guests scan a code and get a stripped-down page that can only add to the queue — no login, no app, no access to anything else. You keep veto rights. Solves a real problem that every host has.

Your own listening year

Medium payoffLow effort

Every play is logged on your own hardware. Real statistics from complete data, private by construction — and honest, unlike the marketing exercise you get from a streaming service. Sync to ListenBrainz if you want open recommendations back.

An ambient now-playing display

CharmingScope creep

The spare Pi and a small panel or e-ink frame showing cover art and level meters, turning the system into a visible object in the room. Genuinely lovely. Also entirely optional — do it after v1 actually works, or it will eat v1.

06 — Briefing

How to hand this to Claude Code

Don't ask for the whole application in one prompt. Split it into three briefs that can each be judged on their own.

Brief one — the engine, headless

A typed API client plus a playback engine with no interface at all: gapless scheduling through Web Audio, prefetch of the next track, ReplayGain application, Media Session wiring, and a server-authoritative queue. Ask for a test harness. Gapless bugs are the ones that will eat your weekends, and they are completely invisible in a screenshot — which means they are invisible to a model reviewing its own work visually.

Brief two — the design system, before any screens

Give constraints, not adjectives. Dark-first, because people listen in the evening. Artwork is the largest element on every surface. One accent, derived from the current cover. Typography that survives a ninety-character classical track title without truncating into nonsense. Works at 400px and at 2000px. No CDN dependency of any kind, because this runs on a machine that may have no internet.

Ask for a token file and two or three static screens as plain HTML before a single component gets written. It is much cheaper to reject a direction at that stage.

Brief three — screens, one at a time

Album view. Full-screen now-playing. Search. Queue. In that order, each against the finished token file. Resist asking for all four at once; the fourth will always be the weakest and you'll keep it anyway.

07 — Start here

The first five moves

  1. Order an SSD. The 64GB card is a dead end and everything you build on it has to move later anyway.
  2. Run your existing FLACs through beets on your laptop — tags, artwork, ReplayGain, one folder convention — before anything reaches the Pi.
  3. Stand up Navidrome on the Pi, on Ethernet, and listen to your library through any existing Subsonic client. You now have a working system, and everything after this is improvement rather than prerequisite.
  4. Build the headless playback engine and prove gapless works on a live album. If this doesn't work, nothing else matters.
  5. Only then design a single screen — the album view — and see whether you like using it enough to build the other three.
